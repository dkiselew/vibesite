# PRD — Web Docs Stage 1

**Статус:** спецификация запуска. Не vision.
**Источник:** [design-document.md](./design-document.md), [constitution.md](./constitution.md)
**Контракты:** [contracts.md](./contracts.md)
**UX:** [ux-spec.md](./ux-spec.md)
**Дата:** 2026-09-18

Цель Stage 1: документ из Cursor / Claude / ChatGPT / Алисы становится файлом в папке со стабильным URL. Папка может быть общей для организации. Без своего ИИ, git, билда и «проекта». Повторная заливка не рождает новый адрес.

Критерий, что Stage 1 живой (не в этом PRD закрывать числом): не «один раз получили URL», а люди **держат документы в общей папке** и каждую неделю делают **Replace по той же ссылке**.

---

## Персоны

| Кто | Работа |
|---|---|
| **Owner** | Создал workspace. Кладёт HTML, приглашает в папку, перевыпускает MCP-ключ. |
| **Member** | В той же папке. Кладёт HTML, Replace / Duplicate / Delete. Не приглашает и не снимает людей. |
| **Агент** | Cursor / Claude с MCP. Пишет на диск workspace по общему ключу. |
| **Получатель** | Открывает ссылку. Аккаунта нет. Ничего не правит. |

ChatGPT и Алиса в Stage 1 агентами не являются: только copy/download HTML → paste/drop в UI.

---

## Scope

Входит: аккаунт, workspace, общая папка организации (invite / accept / leave / remove), список, drop/paste, MCP-диск, публичный URL, Open, Copy link, Replace, Duplicate, Rename, Delete, ключ MCP, гигиена ссылки (OG, noindex, без JS на выдаче), плашка Free на публичной странице.

Не входит: пароль, unlisted, открытия, свой домен, снятие плашки, срок жизни ссылки, именованная история снимков, роли на документе, вложенные папки, биллинг, свой ИИ, шаблоны (Stage 2), редактор, markdown, git, кастомный GPT как зависимость запуска.

Свой домен — оффер Pro, не этот PRD. Общая папка — этот PRD.

---

## Решения Stage 1

Зафиксированы здесь, чтобы агент не выбирал продукт. Смена — правка PRD.

| Тема | Решение |
|---|---|
| Аккаунт | Вход по magic link на email. Owned workspace — не больше одного. Членств в чужих папках — сколько пригласили. |
| Слаг workspace | Задаётся, только если человек создаёт свою папку. Уникален, становится субдоменом, в Stage 1 **не меняется**. Кто пришёл по invite — слаг не выбирает. |
| Общая папка | Один список и одно URL-пространство на всех членов. Owner приглашает по email. Member = полный диск документов, не каретка. |
| Новый workspace | Второй owned workspace в Stage 1 **не создаём**. Switcher — если членств больше одного. |
| Видимость | Все документы публичны по URL. Кто знает путь — читает. |
| Индексация | Все документы `noindex`. Переключатель индексации — не Stage 1. |
| Плашка | На публичной выдаче Free — небольшая плашка Web Docs (не в сохранённом файле). Превью из списка её тоже показывает. |
| Ассеты | Только то, что внутри HTML: `data:` и внешние `https:` картинки/шрифты/CSS. Отдельной загрузки файлов нет. |
| Rename | Меняет сегмент URL. Старый путь даёт 404, пока имя снова не займут. Редиректа нет. |
| Delete | Сразу. Имя можно занять снова. Корзины нет. |
| Confirm Replace | Только в UI и только если у документа уже копировали ссылку. MCP `put_document` не спрашивает. |
| Язык UI | Английский. |

## Истории

Идентичность документа: `(workspace_slug, name)`. Имя — без `.html`.

Документные истории (P1–P15, кроме P0 и P13 regenerate) выполняет любой член папки: owner или member.

### P0. Owner получает workspace

**Given** человек открыл приложение без сессии и без приглашения  
**When** вводит email и переходит по magic link, затем выбирает свободный слаг workspace  
**Then** создаётся аккаунт, workspace, membership role=owner, пустой список  
**And** слаг соответствует правилам имён из contracts  
**And** повторный вход попадает в тот же workspace, слаг не предлагается снова

Acceptance:

- Нельзя создать второй workspace с тем же слагом.
- Слаг становится субдоменом (`https://{slug}.{host}/…`). Имена вроде `login` допустимы — reserved-списка нет.
- Выйти и войти — те же документы.
- Второй owned workspace создать нельзя.

### P1. Пустой список понятен

**Given** workspace без документов  
**When** автор открывает приложение  
**Then** видит папку документов (не «create a site») и два входа: drop `.html` / paste HTML  
**And** видит, где взять MCP-ключ (settings)

Acceptance:

- Нет мастера шаблонов, чата, «generate page».
- Есть короткая подсказка: собери HTML в своём ИИ → положи в эту папку.

### P2. Создать документ drop-ом

**Given** автор в списке  
**When** бросает файл `cv.html`  
**Then** создаётся документ `cv`  
**And** канонический URL `https://{workspace}.{host}/cv`  
**And** документ сразу в списке и уже живой (получатель может открыть)

Acceptance:

- Имя из файла, нижний регистр, без `.html`.
- Если имя занято — не затирает молча: ошибка, предложить Replace или другое имя (см. UX).
- Не `.html` → отказ, файл не создаётся.
- Файл больше лимита → отказ.

### P3. Создать документ paste

**Given** автор вставляет HTML в поток «новый документ»  
**When** подтверждает имя (подсказка из `<title>` или `document`)  
**Then** документ создан и живой, как в P2

Acceptance:

- Полный HTML сохраняется как есть.
- Фрагмент без `<html>` оборачивается минимальной оболочкой (contracts).
- Пустая вставка → отказ.

### P4. Агент кладёт документ через MCP

**Given** агент знает ключ workspace  
**When** вызывает `put_document` с `name: "incident-db"` и HTML  
**Then** в ответе канонический публичный URL  
**And** GET этого URL отдаёт документ (с политикой выдачи)  
**And** документ виден всем членам этой папки в списке

Acceptance:

- Повторный `put_document` с тем же именем = Replace, URL тот же.
- Неверный ключ → ошибка авторизации, файл не пишется.
- Те же правила имён и лимитов, что в UI.

### P5. Открыть = публичная страница

**Given** документ `cv` существует  
**When** автор нажимает Open  
**Then** новая вкладка открывает канонический URL  
**And** содержимое, CSP, noindex и плашка совпадают с тем, что увидит получатель

Acceptance:

- Нет отдельного preview: Open открывает тот же origin, что и получатель (`https://{workspace}.{host}`).
- Origin приложения (`{host}`) документ не отдаёт.
- Редактора исходника нет.

### P6. Скопировать ссылку

**Given** документ в списке  
**When** автор копирует ссылку  
**Then** в буфере канонический HTTPS URL  
**And** документ помечается как «ссылку копировали» (для confirm Replace)

Acceptance:

- Копирование — единственный триггер флага. Open флаг не ставит.
- MCP `put_document` / `get_document` флаг не ставят.

### P7. Replace в UI

**Given** документ существует  
**When** автор выбирает Replace и даёт новый HTML (файл или paste)  
**Then** GET того же URL отдаёт новое содержимое  
**And** строка URL не меняется  
**And** дата изменения в списке обновляется

Acceptance:

- Если ссылку уже копировали — без подтверждения Replace не выполняется.
- Если ссылку не копировали — подтверждение не требуется.
- Имя и workspace не меняются.
- Лимит размера тот же, что при создании.

### P8. Duplicate

**Given** документ `cv`  
**When** автор делает Duplicate  
**Then** в списке новый документ с новым именем и новым URL  
**And** исходный `cv` не изменился  
**And** копия содержит тот же сохранённый HTML  
**And** у копии флаг «ссылку копировали» = false

Acceptance:

- Имя по правилу `cv-YYYY-MM-DD`, при занятости `cv-YYYY-MM-DD-2`, …
- Копия — обычный документ: её можно Replace, шарить, удалить.
- Это не hidden revision и не git.

### P9. Rename

**Given** документ `cv`  
**When** автор переименовывает в `resume`  
**Then** живой URL становится `https://{workspace}.{host}/resume`  
**And** `https://{workspace}.{host}/cv` отвечает 404, пока имя `cv` снова не займут  
**And** редиректа `/cv` → `/resume` нет

Acceptance:

- Новое имя должно быть свободно и валидно.
- Флаг «ссылку копировали» сбрасывается (это уже другой адрес).
- В списке меняются имя и отображаемый URL.

### P10. Delete

**Given** документ `cv`  
**When** автор подтверждает удаление  
**Then** документ исчезает из списка  
**And** GET `https://{workspace}.{host}/cv` — 404  
**And** имя `cv` можно снова создать

Acceptance:

- Без подтверждения не удалять.
- MCP `delete_document` подтверждение UI не показывает; ключ = полномочие.

### P11. Получатель читает

**Given** известен публичный URL  
**When** получатель открывает его без аккаунта  
**Then** видит HTML как документ: вёрстка автора, без каретки  
**And** авторский JS не исполняется  
**And** в превью мессенджера есть заголовок (из `<title>` или имя документа)

Acceptance:

- 404 — обычная страница «нет документа», без списка чужого workspace.
- Нет форм логина поверх чужого CV (плашка Free — исключение, см. UX).

### P12. MCP как диск

**Given** валидный ключ  
**When** агент вызывает `list_documents`, `get_document`, `put_document`, `duplicate_document`, `delete_document`  
**Then** поведение совпадает с UI по данным (не по confirm-диалогам)

Acceptance:

- Схемы и ошибки — только из contracts.
- Нет tool `publish` / `deploy`.
- `get_document` возвращает **сохранённый** HTML, не обязательно байты с публичной выдачи (санитизация на выдаче может отличаться; файл на диске — оригинал).

### P13. Ключ workspace

**Given** член папки открыл Settings  
**When** смотрит MCP key  
**Then** видит текущий ключ и канонический URL MCP endpoint

Acceptance:

- Ключ один на workspace. Его видят все члены.
- Перевыпускает только owner (старый перестаёт работать). Member не видит Regenerate.
- Ключ не логировать в публичные документы и OG.

### P14. Гигиена выдачи

**Given** в HTML есть `<script>`, `onclick`, формы, `<base>`  
**When** получатель открывает публичный URL  
**Then** скрипты и обработчики не исполняются, формы не уходят, base не перехватывает относительные URL  
**And** сохранённый оригинал через `get_document` остаётся

Acceptance:

- Политика — contracts (CSP + санитизация выдачи).
- OG: `og:title` из `<title>`, иначе имя документа; `og:description` из `meta name="description"` / `og:description`, иначе отсутствует.
- `X-Robots-Tag: noindex` на всех документах.

### P15. Лимиты Free

**Given** workspace на Free  
**When** автор превышает число документов или размер файла  
**Then** создание / Replace / Duplicate отклоняется с понятной ошибкой  
**And** уже лежащие документы продолжают открываться

Числа — в contracts. Менять числа можно без смены историй.

### P16. Owner приглашает в папку

**Given** owner в своём workspace  
**When** вводит email коллеги и отправляет приглашение  
**Then** на этот email уходит magic link / invite  
**And** в Settings виден pending member

Acceptance:

- Повторный invite на тот же email, пока pending — обновляет ссылку, не плодит членство.
- Email уже member → ошибка, второе членство не создаётся.
- Свой email → отказ.
- Лимит членов → `limit_exceeded`, письмо не уходит.
- Member не видит форму Invite и не может пригласить.

### P17. Новый человек принимает приглашение

**Given** аккаунта ещё нет, есть действующее приглашение  
**When** человек открывает invite-ссылку и подтверждает email  
**Then** создаётся аккаунт и membership role=member  
**And** он попадает в список этой папки, без экрана слага  
**And** owned workspace у него нет

Acceptance:

- Слаг чужой папки не предлагается и не меняется.
- Просроченное приглашение → ошибка, членства нет.
- После accept повторный вход открывает эту папку.

### P18. Существующий человек принимает приглашение

**Given** у человека уже есть свой workspace  
**When** он принимает приглашение в чужую папку  
**Then** появляется второе членство  
**And** он может переключить папку  
**And** документы его owned workspace не смешиваются со списком чужой папки

Acceptance:

- Switcher виден только если членств больше одного.
- Текущая папка — сессия. Документные действия пишут только в неё.
- Создать ещё один owned workspace по-прежнему нельзя.

### P19. Member работает с тем же диском

**Given** member в общей папке, документ `offer` уже лежит  
**When** он делает Replace / Duplicate / Rename / Delete или агент с ключом workspace делает `put_document`  
**Then** список и публичный URL меняются так же, как если бы это сделал owner  
**And** другие члены видят тот же результат

Acceptance:

- Confirm Replace смотрит на `link_copied_at` документа, не на то, кто копировал.
- MCP-ключ один на папку: агент member'а пишет в ту же папку.
- Получатель по URL не видит, кто из членов положил файл.

### P20. Убрать человека из папки

**Given** в папке есть member  
**When** owner удаляет его  
**Then** у человека больше нет доступа к списку и Settings этой папки  
**And** ключ MCP не меняется  
**And** документы остаются

Acceptance:

- Удалённый не видит папку в switcher.
- Его сессия на эту папку сбрасывается на другой membership или на пустое состояние «нет папки» (если других нет — только logout / ждать новое приглашение; новый owned workspace не создаём молча).
- Member может сам Leave. Owner — нет, пока он единственный owner.
- Owner не может удалить себя, если он последний owner. Передачи ownership в Stage 1 нет.

### P21. Сменить папку

**Given** у человека два членства  
**When** он выбирает другую папку в switcher  
**Then** список, URL-префикс и MCP-ключ в Settings принадлежат выбранной папке

Acceptance:

- Случайный drop не пишет в только что покинутую папку.
- Публичные URL не зависят от того, какая папка открыта в приложении.

## Негативные случаи (обязательны)

| Случай | Ожидание |
|---|---|
| Чужой MCP-ключ | 401/403, нет листинга чужого workspace |
| Человек не член папки | нет списка, нет Settings этой папки, нет UI-мутаций |
| Member зовёт Invite / Regenerate / Remove | отказ, диск не меняется |
| Просроченный invite | членства нет |
| Подбор URL чужого документа | Если угадал имя — прочитает (публично). Перебора списка без ключа нет |
| Имя `cv.html` в MCP | Нормализация: сохраняем как `cv`, либо ошибка `invalid_name` — см. contracts: **нормализуем, один раз снимаем `.html`** |
| Имя документа `login` / `settings` | Обычный документ на субдомене, не ошибка |
| Одновременный Replace | Последняя успешная запись выигрывает; URL тот же; без ветвления |
| Битый HTML | Принимаем как текст; на выдаче всё равно CSP. Не «чиним» DOM автора |

## Метрика запуска (продукт, не аналитика в UI)

Stage 1 живой, когда **в одной папке работают несколько людей организации** и повторяют Replace по тому же URL.

В продукте Stage 1 **нет** счётчика открытий (это Pro). Для dogfood достаточно: двое из канала 1 кладут документы в общую папку и на следующей неделе делают Replace.

---

## Вне скоупа (явный отказ)

Если задача просит любое из этого — отказ, не «потом в том же PR»:

- пароль, unlisted, истечение ссылки
- просмотры / «открыл ли рекрутер»
- custom domain, снятие плашки — оффер продукта, не этот PRD
- роли на документе, viewer-only, вложенные папки, второй owned workspace
- передача ownership
- редактор, чат, markdown, git
- шаблоны и правки на залитой странице — Stage 2 (design document), не этот PRD
- Stage 2
- кастомный GPT / коннектор ChatGPT как блокер
- индекс документов по `https://{workspace}.{host}/`
- загрузка картинок отдельными файлами

## Открытые вопросы (не блокируют Stage 1)

1. Боевой hostname (`webdocs.app` или другой) — решение деплоя, грамматика URL от этого не меняется.
2. Число N для «Stage 1 живой» — операционное, не продуктовое поведение.
3. Нужен ли позже GitHub OAuth вдобавок к magic link — не в этом релизе.
4. Точные тексты legal (ToS: автор отвечает за содержимое) — нужны к публичному запуску, не к схеме данных.
